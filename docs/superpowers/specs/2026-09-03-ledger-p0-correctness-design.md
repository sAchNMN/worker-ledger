# 打工人小账本 P0 正确性修复设计

## 1. 目标与范围

本轮只修复会让账目失真的数据语义、安全边界和对应行为测试，不新增消费前换算器、自定义分类、周期账单、趋势分析或隐私模式。

必须满足：

- 收入和支出使用不同分类；房租默认固定，但用户手动覆盖后保留覆盖结果。
- 日期按真实公历校验；格式正确但不存在的日期必须拒绝。
- 每笔新流水保存发生时的真实时薪快照；修改当前设置不得改写历史流水的工时结果。
- 工资按生效月份计算；生效前、没有工资记录的月份和未来未生效月份不凭空产生工资。
- 备份格式有明确版本和元数据；旧版备份可以迁移，失败导入不得改变现有数据。
- 删除后提供短时撤销；应用进程结束后不承诺跨进程撤销。
- Manifest 关闭 Android 系统备份，保持“用户通过 JSON 手动迁移”的产品承诺。

正式 Release keystore 不在本轮自动生成或提交。密钥必须由用户在本机创建并安全保存；仓库只保留不含密钥的构建说明或可选配置。

## 2. 数据模型与时间语义

### 2.1 数据库版本 2

`LedgerDbHelper.DATABASE_VERSION` 升为 2。新安装直接创建 v2 的全部表；`onUpgrade` 只做可回滚的增量迁移，不删除原表或历史流水。

`ledger_entries` 增加：

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `hourly_rate_cents_per_hour` | `INTEGER` 可空 | 记录保存时的真实时薪，单位为“每小时的分”；为空表示历史上无法获得有效时薪 |

新建流水时，使用保存当下的设置计算该值；真实时薪无效或小于等于 0 时存空值。渲染流水时优先使用该快照，不再使用当前设置回算。

新增 `salary_history`：

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `effective_month` | `TEXT PRIMARY KEY` | `YYYY-MM`，工资从该月开始生效 |
| `monthly_take_home_cents` | `INTEGER NOT NULL` | 该生效记录的综合到手月薪 |
| `created_at` | `INTEGER NOT NULL` | 本地 Unix 毫秒时间戳 |
| `updated_at` | `INTEGER NOT NULL` | 本地 Unix 毫秒时间戳 |

月度工资规则：未来月份不计算工资；当前月及过去月份取 `effective_month <= targetMonth` 的最新一条记录，没有记录则工资为 0。工资历史允许多个生效月份，保存同一月份时覆盖该月份记录。这样查看未来月份不会凭空产生“已赚到的工资”；未来工资计划不在本轮范围内。

当前 `user_settings` 继续保存当前工作参数、工作成本和基金参数。当前参数用于今日时薪和情景模拟；历史流水只读自己的时薪快照，月度工资只读 `salary_history`。

### 2.2 旧数据库迁移

从版本 1 升级时：

1. 给 `ledger_entries` 增加可空时薪快照字段。
2. 按迁移时的当前设置计算有效时薪，为现有流水一次性填入快照；无法计算则填空值。这是“从旧数据无法恢复历史工资”的明确迁移假设，不再随未来设置变化。
3. 创建 `salary_history` 表。
4. 使用旧设置的 `updated_at` 转换为设备本地 `YYYY-MM`，创建一条工资生效记录；旧数据没有更早的工资历史，不能补造。

迁移必须在同一个 SQLite 事务中完成；任何一步失败都不能留下半迁移数据库。

### 2.3 备份格式版本 2

新导出格式保持现有顶层字段兼容，并增加版本和工资历史：

```json
{
  "schemaVersion": 2,
  "exportedAt": 1788393600000,
  "appVersion": "1.0",
  "settings": {},
  "salaryHistory": [
    {"effectiveMonth": "2026-09", "monthlyTakeHomeCents": 1000000}
  ],
  "entries": []
}
```

导入规则：

- `schemaVersion: 2` 必须校验全部字段。
- 没有 `schemaVersion` 的文件按旧版 v1 迁移：流水和当前设置保留，工资历史从导入月份开始建立一条当前工资记录，不能把当前工资倒灌到更早月份。
- 未知的更高版本拒绝导入，不尝试猜测字段。
- 导入先读取、限制大小、解析、校验、生成预览；用户确认后才进入数据库事务。
- 事务内删除旧流水、替换设置、替换工资历史并插入新流水；任意异常自动回滚。

预览至少显示：备份版本、导出时间、流水笔数、最早日期、最晚日期和工资历史条数。

## 3. 页面行为

### 3.1 分类

支出分类固定为：吃饭、交通、购物、娱乐、房租、其他。

收入分类固定为：工资、奖金、兼职、礼金、报销、其他。工资分类允许作为额外收入流水使用，但月度“工资收入”仍来自工资历史，避免同一笔工资被重复理解为系统工资。

编辑历史流水时，如果其分类不在当前固定列表中，页面必须临时保留该名称，不能因为打开编辑页面就把历史分类改成“其他”。自定义分类留到后续版本。

支出默认性质映射只有一条：`房租 -> fixed`，其余支出分类为 `flexible`。分类变更时应用映射；用户随后手动选择固定/弹性后不被重新覆盖，除非用户再次变更分类。

### 3.2 工资生效月份

“我的时薪”表单增加“工资生效月份”，默认当前月份；本轮只允许当前月或过去月份，晚于当前月份的值直接拒绝。保存时同时更新当前 `user_settings` 和该月份的 `salary_history`。基金表单保存时不得新增或修改工资历史。

### 3.3 删除撤销

删除流程为：

1. 读取并保存待删除流水的完整字段。
2. 删除成功后显示约 5 秒的撤销入口。
3. 点击撤销，通过专用恢复接口按原 ID、原时间戳和原字段恢复；恢复失败显示错误且不伪造成功状态。
4. 新增其他流水或撤销窗口到期后清除内存中的待撤销记录。

不增加软删除表；应用重启后不保证恢复已删除流水。

## 4. 校验边界

页面纯函数和 Android 原生层必须执行同一组规则：

- 日期必须严格匹配 `YYYY-MM-DD` 并且是实际公历日期；月份必须严格匹配 `YYYY-MM`。
- 流水类型只能是 `income` 或 `expense`。
- 金额必须是安全范围内的大于 0 的整数分；空值、负数、小数、非有限数和超出安全整数范围均拒绝。
- 分类必须为非空字符串；备注保留长度上限 80。
- 支出性质只能是 `fixed` 或 `flexible`；收入的性质必须为空。
- 工资、工作日、时长、工作成本和基金金额必须为有限非负数；工作日、发薪月数和总时间必须满足计算要求。
- 备份必须是对象，字段类型正确，数组元素完整，流水 ID 在导入文件中唯一且为正整数。

JavaScript 日期校验使用 UTC 年月日往返校验；Android 使用非宽松公历解析并再次比对格式。不能只使用正则表达式。

## 5. 接口边界

保持现有同步本地 Bridge 风格，并新增最少接口：

- `loadSnapshot()` 返回带 `schemaVersion`、`salaryHistory` 和快照时薪的当前数据。
- `saveSettings(json)` 继续保存当前设置，同时读取 `salaryEffectiveMonth` 更新工资历史。
- `insertEntry(json)` 保存当前时薪快照并返回新 ID。
- `updateEntry(json)` 更新流水内容；除非显式重新保存该流水，不改写其原有时薪快照。
- `deleteEntry(id)` 返回被删除的完整流水，而不是空数据。
- `restoreEntry(json)` 只允许恢复刚刚删除的完整流水，并在数据库层校验 ID 不冲突。
- `requestImport()` 读取文件后只产生预览；`confirmImport()` 才执行事务替换。

Bridge 只在内置 `file:///android_asset/` 页面启用，继续拒绝外部 URL，不增加网络权限。`AndroidManifest.xml` 设置 `android:allowBackup="false"`。

## 6. 测试与验收

先写能失败的行为测试，再实现最小代码。Node 测试必须覆盖：

1. 收入切换后只出现收入分类。
2. 房租默认固定，手动覆盖后分类未变时保持覆盖。
3. `2026-02-30` 和 `2026-99-99` 被拒绝，合法闰日被接受。
4. 入职前或工资生效前月份的工资为 0，生效月份及之后才计入。
5. 修改当前时薪后，带有历史快照的流水工时不变。
6. 无版本旧备份迁移后流水和设置仍完整，且不把工资倒灌到历史月份。
7. 导入数据任意一条非法时，旧快照仍保持不变。
8. 删除后撤销恢复原 ID、金额、分类、日期、性质、备注和时间戳。

原生层验收：

- 所有现有 Node 测试通过。
- `:app:assembleDebug --offline` 成功。
- 有 Android 设备或模拟器后，补跑数据库迁移、事务回滚、文件选择器预览确认和撤销交互；没有设备时必须明确标记为未完成，不能用静态字符串测试替代。

不在本轮承诺 Release 安装升级验证，直到用户创建并保管正式 keystore，并将 `versionCode` 管理纳入发布流程。
